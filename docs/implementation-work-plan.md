# План работ: локальный бэкенд и Android-фронтенд

## 1. Назначение

Общий план реализации тестового задания `SC-TA-001`. Серверной части нет:
**бэкенд** — модули `:core:*` и `:seed-generator` (данные, правила, use case);
**фронтенд** — модуль `:app` (Compose UI по макетам).

Источники, в порядке приоритета при расхождении:

1. [`testassignmentexpensetracker.md`](./testassignmentexpensetracker.md) — обязательное поведение и приёмка.
2. [`categorization-architecture.md`](./categorization-architecture.md) и [`android-architecture-dependencies.md`](./android-architecture-dependencies.md) — устройство слоёв.
3. [`seed-dataset-plan.md`](./seed-dataset-plan.md) — датасет 1 000 строк, генерация seed и поставка.
4. Figma — экраны, состояния и визуальный язык.

Ориентир ТЗ: **30–40 часов**, **7 календарных дней**. Бонусы (B-01…B-03) не входят
в этот план. Инфраструктура (окружение, эмулятор, линтер, CI) входит с дня 1:
без неё нельзя ни гонять UI, ни сдавать воспроизводимую сборку (NFR-8, NFR-9, B-04).

## 2. Как читать макеты

Файл: [Expense Tracker Android MVP](https://www.figma.com/design/SDEMi6JxeVMZZ0Om1Xi3tY/Expense-Tracker-Android-MVP).

Destination Navigation 3 (как в `AD-ANDROID-001`): **Расходы, Редактирование расхода,
Аналитика, Категории, Настройки**. Остальное — `ModalBottomSheet` / `AlertDialog`.

Форма Quick Add в Figma — полноэкранный кадр 360×800, а не sheet. Реализуем как
полноэкранный overlay/destination; keypad суммы, календарь, фильтры, периоды,
выбор категории и подтверждения остаются панелями.

При конфликте двух страниц Figma:

- список, аналитика, архив, ошибки файлов, empty/loading — **MVP Screens**;
- вход в настройки (шестерёнка в app bar), picker категорий, создание категории
  из расхода, счётчик правил — **UX Flow**.

- настройки открываются с любой корневой вкладки через app bar.

## 5. Инфраструктура (окружение, эмулятор, CI)

Основной цикл разработки — эмулятор. Юнит-тесты JVM не требуют устройства.
Телефон нужен один раз в день 7 для NFR и чеклиста §5 ТЗ.

### Этап I0. Локальное окружение — 1–1,5 ч

Статус: выполнено 2026-09-03.

- JDK 17, Android Studio, Android SDK, platform-tools.
- Gradle Wrapper в репозитории; версии только в `libs.versions.toml`.
- `local.properties` в `.gitignore`; в README — шаблон без секретов.
- Debug-сборка на стандартном debug keystore. Релизный ключ и Play Console
  не настраиваем.
- Команды в README: `./gradlew :app:assembleDebug`, `./gradlew test`,
  `./gradlew lint`, `./gradlew :app:installDebug`.

DoD: чистый клон собирается без ручных правок исходников (NFR-9).

### Этап I1. Эмулятор Android — 1–1,5 ч

Статус: выполнено 2026-09-03.

Один основной AVD, совпадающий с макетом:

| Параметр | Значение |
|---|---|
| Имя | `ExpenseTracker_360` |
| Размер | 360×800, density 420 dpi (как кадры Figma) |
| API | 34 (или актуальный стабильный), образ Google APIs x86_64 |
| Навигация | жестовая |
| Вырез | обычный punch-hole / «вырез», чтобы сразу видеть safe area |
| RAM | 2–3 ГБ, достаточно для списка на 5 000 |

Создать через Device Manager или `avdmanager`. Зафиксировать в README:
имя AVD, API, как стартовать (`emulator -avd ExpenseTracker_360`).

На эмуляторе ежедневно:

- `./gradlew :app:installDebug` и запуск приложения;
- режим полёта для F-08;
- переключение системной светлой/тёмной темы;
- SAF для экспорта и backup/restore (файлы на эмуляторе).

Инструментальные тесты Room/FTS и короткие Compose UI-потоки гонять
только на этом AVD, не в CI.

Второй AVD и физический телефон в ежедневный цикл не входят.

DoD: пустой каркас `:app` ставится на AVD и открывает три вкладки.

### Этап I2. Статический анализ и локальный `check` — 1 ч

Статус: выполнено 2026-09-03.

- ktlint или detekt + Android Lint; порог — ноль ошибок (NFR-8).
- `./gradlew check` = lint + unit-тесты JVM всех модулей.
- Baseline Lint допустим только для шума сторонних библиотек,
  не для своего кода.
- Pre-commit хуки не ставим: достаточно CI и локального `check`.

DoD: `./gradlew check` зелёный на пустом каркасе и остаётся обязательным
после каждого этапа.

### Этап I3. CI/CD — 1,5–2 ч

GitHub Actions (или аналог хостинга репозитория). Публикация в магазины
не входит.

На каждый push и pull request:

1. checkout + JDK 17 + cache Gradle;
2. `./gradlew check` (lint + JVM-тесты);
3. `./gradlew :seed-generator:generateSeed` (после этапа B3);
4. проверка, что `app/src/main/assets/seed/` совпадает с генерацией;
5. `./gradlew :app:assembleDebug`;
6. загрузка APK как artifact workflow (7 дней хранения).

Не включать в CI:

- эмулятор и instrumentation — долго и нестабильно на бесплатных runner;
- `assembleRelease` и подпись — нет релизного ключа;
- деплой на устройство или в Firebase App Distribution.

Пайплайн заводится в день 1 на пустом каркасе и наращивается тестами
вместе с B3/B6. К сдаче в README — бейдж статуса и как скачать APK
из последнего успешного прогона.

DoD: красный PR при падении теста или lint; debug APK скачивается из CI
без локальной машины.

### Этап I4. Приёмка на эмуляторе и телефоне — 1–1,5 ч

День 7, после F7.

На основном AVD — полный чеклист §5: ввод, автокатегория, список,
аналитика → срез, категории, файлы, обе темы, airplane mode.

На телефоне, если есть, один проход Must + NFR-1/NFR-2/NFR-7
(холодный старт, 5 000 записей, вырез). Если телефона нет — в README
явно: проверено на AVD `ExpenseTracker_360`, API 34; NFR на среднем
устройстве не замерялись. Проверяющие всё равно ставят APK на своё
устройство.

Запись 2–4 минут демо — с эмулятора достаточно.

## 6. Бэкенд (`:core:*`, `:seed-generator`)

### Этап B0. Каркас модулей — 3–4 ч

- Gradle-проект, Version Catalog, модули из `AD-ANDROID-001`.
- `:core:model`: `Expense`, `Category`, `Location`, `Money`, `Period`,
  `CategorizationResult`.
- Composition root `AppContainer` без Hilt/Koin.
- Первая Room-миграция: пустая схема → таблицы §7 `AD-CAT-001`.
- Bundled SQLite + FTS5.
- 10 встроенных категорий из макета — коды и имена из
  [`seed-data/categories.yaml`](../seed-data/categories.yaml). `Прочее` защищена.
- Каталог `seed-data/` по [`seed-dataset-plan.md`](./seed-dataset-plan.md): `categories.yaml`,
  `raw/train.csv` минимальный (~30 строк) для cold start на «латте / аптека / бензин».
- Stub seed-артефакт в `app/src/main/assets/seed/` (импорт при первом запуске).

DoD: приложение стартует, БД создаётся, категории видны через repository;
`seed-data/` и stub assets в репозитории.

### Этап B1. Расходы, места, валидация — 3–4 ч

Use case:

- создать / изменить / удалить расход;
- валидация суммы: пустая, 0, отрицательная, нечисло — ошибка поля;
- дата по умолчанию — сегодня; политика будущей даты — **запрет**
  (одинаково во всех формах);
- `amount_minor`, `dedup_key`, `category_assignment_source`;
- автодополнение места: prefix + FTS, сортировка `last_used_at`, `usage_count`;
- атомарная транзакция «расход + место + обучение» из §11.2 `AD-CAT-001`.

DoD: расход переживает перезапуск; повторное сохранение без изменений
не увеличивает счётчики.

### Этап B2. Категории — 2–3 ч

- единый список активных, бейджи только отображаются;
- создание/правка только пользовательских;
- автоподбор `category.icon` по нормализованному имени, fallback `letter`;
- пустое и дублирующее имя — отказ;
- архив реактивирует строку с тем же `normalized_name`;
- soft delete: расходы и правила сохраняются; fallback не архивируется;
- создание категории даёт `source=category_name` и category alias.

DoD: удаление категории не теряет расходы; реактивация возвращает тот же `id`.

### Этап B3. Категоризация, seed-генератор и runtime-обучение — 8–10 ч

Чистый `:core:categorization`, без Android API, плюс `:seed-generator` по
[`seed-dataset-plan.md`](./seed-dataset-plan.md).

**CategorizationEngine и runtime-обучение:**

1. `TextNormalizer` + Snowball (скопированный исходник, не Lucene).
2. Последовательность §10.1: local exact → alias → seed exact → векторы → fallback.
3. Exact rule только после явного выбора или исправления.
4. Принятая автоподстановка пишет `learning_example` и `name_category_context`,
   но не exact rule.
5. Транзиты для полностью перешедших слов.
6. `CategorizationResult` с `source`, `confidence`, `orderedCandidates`,
   `matchedFeatures` — фронт показывает подпись как в `116:6` / `117:2`.
7. Импорт и фоновый пересчёт не обучают.
8. F-11: очистка расходов обнуляет `expense_id`, правила остаются.
9. Счётчик запомненных правил для строки настроек.
10. Импорт seed из `assets/seed/` при первом запуске; идempotent update §15 `AD-CAT-001`.

**Seed-датасет и `:seed-generator`:**

1. Полный `seed-data/raw/train.csv` — **800 строк** (80 на категорию).
2. `seed-data/raw/validation.csv` — **200 строк** (20 на категорию), без пересечения
   с train по `normalized_name`.
3. `:seed-generator`: `DatasetReader`, `CounterBuilder`, `ContextBuilder` (контексты
   для транзитов §19.7), `SeedFilter`, `ValidationRunner`, `SeedArtifactWriter`.
4. Gradle-задача `:seed-generator:generateSeed` → `app/src/main/assets/seed/`.
5. Grid search параметров на validation; фиксация в `seed-data/categorization-config.json`.
6. Целевые метрики: top-1 ≥ 85 %, fallback OTHER < 15 %.
7. Golden-строки из §5.2 seed-плана покрыты unit-тестами.

Параметры — одна версионированная конфигурация, не размазаны по коду.

DoD: unit-тесты §18 `AD-CAT-001`; seed v1 из 1 000 строк сгенерирован и закоммичен;
«Латте» → Кафе, «врач / стоматолог» — корректно. Главный инженерный риск задания.

### Этап B4. Список, поиск, аналитика — 3–4 ч

- группировка по дням, свежие сверху; «Сегодня» / «Вчера»;
- сумма текущего среза;
- комбинируемые фильтры: период, несколько категорий, место, текстовый поиск;
- индексы §14; поиск < 300 мс на 5 000 записей;
- аналитика: сумма и доля по категории, общий итог;
- периоды: текущий/прошлый месяц, год, всё время, произвольный диапазон;
- нормализация инвертированного диапазона;
- F-07: те же `categoryIds` + `Period` уходят в список.

Расчёт в `:core:domain`. Vico/Canvas только рисуют готовую модель.

### Этап B5. Экспорт, backup, restore, очистка — 3–4 ч

- CSV расходов со всеми значимыми полями, включая категорию;
- JSON backup: расходы, категории, места, exact rules, context, examples,
  транзиты, версии схемы/нормализатора/seed;
- restore во временную БД / транзакцию; валидация до записи;
- дедуп по UUID и `dedup_key`; повтор не удваивает историю;
- битый файл → понятная ошибка, текущие данные нетронуты;
- очистка истории с сохранением обучения и категорий.

DoD: сценарии F-09…F-11 из §5 ТЗ закрыты тестами round-trip.

### Этап B6. Тесты бэкенда и демо-данные — 2–3 ч

- JVM unit: нормализатор, движок, агрегация, валидация, CSV/JSON, seed import.
- Golden-тесты seed-генератора и приложения на одном нормализаторе (§18.1 `AD-CAT-001`).
- Одна описанная миграция или механизм миграций.
- **Demo-данные для UI отдельно от seed:** скрипт/файл на несколько сотен расходов
  с суммами и датами для списка и аналитики (не путать с `seed-data/`).
- Отдельный набор ~5 000 записей для замера NFR-2 — генерировать локально,
  не коммитить тяжёлый дамп.

DoD: пустые три вкладки + настройки открываются в обеих темах.

### Этап F1. Список расходов — 3–4 ч

Экраны `14:2`, `99:768`, `99:690`, `99:817`.

- заголовок, период, итог среза;
- поиск и чипы; активные фильтры видны без панели;

DoD: 5 000 записей скроллятся без заметных пауз.

### Этап F2. Quick Add и Edit — 5–6 ч

Экраны `27:100`–`27:104`, `40:338`, `147:929`, плюс UX Flow `116:6`, `117:2`,
`118:2`, `147:977`.

Поля: сумма, дата, название, категория, место, комментарий.

- полная форма сразу; тап по сумме → keypad; тап по дате → календарь;
- ошибки суммы у поля, кнопка Save disabled, данные не сбрасываются;
- категория предзаполнена, подпись источника как в макете;
- picker: «Подходят лучше» с score + полный список + поиск + «Создать категорию»;
- создание категории не закрывает расход: новая категория становится выбранной;
- автодополнение места из истории;
- удаление — `DestructiveDialog`, только после подтверждения.
